# source.md

## 역할

- `channels`는 메시징 채널과 외부 대화 입력 수단을 담는 폴더입니다.

## 현재 중심 구현

- 현재는 Telegram, Slack, Discord, Google Chat, iMessage, KakaoTalk 구현을 공통 채널 계약으로 맞춰가는 단계입니다. iMessage/KakaoTalk은 로컬 앱/Yeonjang bridge 의존성이 있는 local bridge 계층으로 취급합니다.
- 채널 시작 처리와 채널별 응답/승인 흐름을 제공합니다.
- 공통 채널 계약은 `contracts.ts`에 정의합니다. 신규 외부 채널은 provider raw payload를 `InboundEnvelope`/`InteractionEnvelope`로 정규화한 뒤 core 실행 계층으로 넘겨야 하며, raw payload 원문은 `RawPayloadRef`의 redacted preview 또는 외부 저장소 ref로만 표현합니다.
- `contracts.ts`는 외부 provider(`ChannelProvider`)와 내부 surface(`ChannelSurface`: WebUI/CLI)를 분리합니다. 실행/전달 호환 값은 `ChannelSource`를 쓰되, 신규 provider별 분기는 registry/capability 단계에서만 추가해야 합니다.
- `connections.ts`는 Telegram/Slack/Discord/Google Chat/iMessage/KakaoTalk 설정을 공통 `channel_connections` 모델로 투영합니다. token은 raw 값이 아니라 `config:<provider>.<key>` secret ref로만 저장하고, allowed user/room은 `provider:kind:id` namespace 식별자로 저장합니다.
- `registry.ts`와 `runtime.ts`는 provider factory, runtime start/stop, health/capability summary, runtime event 기록을 담당합니다. `channel_registry_runtime` feature flag가 `enforced`일 때만 registry runtime으로 시작하고, 기본값/off/rollback/shadow/dual_write는 기존 Telegram/Slack 직접 runtime 경로를 사용합니다.
- 신규 provider를 붙이기 전에는 `tests/fixtures/channel-adapter-contract-runner.ts`의 contract runner와 provider fixture를 먼저 추가해야 합니다. 이 runner는 `capabilities`, `normalizeInbound`, `normalizeInteraction`, `sendMessage`, `handleInteraction`, raw payload redaction, unsupported capability fallback을 네트워크 없이 검증합니다.
- `telegram/adapter.ts`, `slack/adapter.ts`, `discord/adapter.ts`, `google-chat/adapter.ts`, `local-bridge/adapter.ts`는 provider별 `ChannelAdapter` facade입니다. 각 provider payload를 `InboundEnvelope`/`InteractionEnvelope`로 정규화하고, continuation 후보, connection policy, capability/health manifest, sent 중심 delivery receipt 정책을 제공합니다.
- `delivery-fallback.ts`는 채널별 `maxMessageLength`, 파일/버튼/스레드/typing capability, artifact 민감도에 따라 긴 텍스트 split, summarize-and-link, download link/native file fallback, explicit approval 필요 여부, `unsupported_capability` UI/receipt 메시지를 결정하는 순수 helper입니다. provider 차이는 실행 실패가 아니라 fallback receipt와 ledger/detail evidence로 표현해야 합니다. Telegram 외부 파일 전달은 캡처와 별도인 moderate-risk operation이며 dispatcher approval을 거쳐야 합니다.
- `smoke-runner.ts`는 WebUI/Telegram/Slack 자동 또는 반자동 smoke, Discord/Google Chat fixture smoke, iMessage/KakaoTalk manual local bridge gate를 같은 scenario 모델로 관리합니다. WebUI와 Telegram은 `basic_query`, `web_skill`, `approval_required_tool`, `artifact_delivery`, `failure_tool` 5종을 공통 Application verifier로 검증합니다. release gate는 scenario 누락/skip/failure, long text, artifact, approval, continuation, duplicate delivery, unsupported capability fallback 회귀를 함께 확인해야 합니다. Gateway 재시작에서는 현재 프로세스보다 먼저 시작된 Gateway 소유(`webui`, `release-live-acceptance`) 진단 run을 `gateway_restart_interrupted`로 원자적으로 종료하며, 별도 프로세스가 소유한 CLI smoke run은 변경하지 않습니다.
- `VerifyConversationProcessUseCase`는 채널별 자연어 의미를 판정하지 않습니다. 시작 시 받은 run/request-group/session과 관찰 결과의 exact binding, canonical LLM receipt 순서, root finalization, 단일 final answer, request delivery state와 visible delivery post-check를 공통으로 검증합니다. 실행형 acceptance가 `requiresDistinctDecisionReceipts`를 명시하면 request diagnosis와 solution plan은 서로 다른 opaque receipt ID여야 하며, generic direct conversation의 simplified cycle은 별도 제품 결정 전까지 기존 opt-in 계약을 유지합니다. transport acknowledgement만으로는 전달 또는 사용자 목표 완료가 되지 않습니다.
- live decision receipt reader는 request-group에 결속된 intake receipt와 run에 결속된 실행·검토·최종응답 receipt를 같은 exact run/group 범위에서 결합합니다. 기존 분리형 `request_diagnosis -> solution_plan -> result_diagnosis -> final_response` 호출과 단순화된 `task_intake(진단+계획) -> completion_review -> final_response` 호출을 모두 하나의 순서 검증 계약으로 투영하며, 단일 `task_intake`만 끝난 대화형 응답은 direct-response receipt로 유지하고 실행 receipt를 만들어내지 않습니다.
- live latency 판정은 first response와 terminal response를 분리하고 exact run의 LLM stage count를 함께 확인합니다. 지연 상태와 실제 밀리초는 release evidence로 보존하지만 verified terminal completion을 latency budget 초과만으로 실패로 바꾸지 않습니다. 같은 evidence revision의 `response_only -> completion_review` 반복은 문구가 달라도 한 transition으로 진단하며, provider timeout이나 retry 횟수만으로 사용자 workflow를 포기하지 않습니다.
- actionable 요청은 model intake의 reject나 `failed_receipt`로 조기 종료하지 않습니다. model response schema는 내부 failure receipt를 허용하지 않으며 invalid category/mode/decision은 bounded typed issue로 한 번 LLM repair합니다. parser는 이를 다른 의미로 자동 보정하지 않습니다. 유효한 intake는 `task_intake`로 실행을 시작하고, policy/capability/execution/completion 경계가 서로 다른 허용 경로와 근거를 검토한 뒤에만 canonical failure를 만들 수 있습니다.
- failure smoke는 모호한 “지원하지 않는 기능” 문장이나 필수 exclusive 호출이 아니라, 공통의 명시적 nonexistent stable method를 우선 방법으로 지정합니다. 따라서 정책은 기능 부재를 추가 입력으로 바꾸지 않고 허용된 대체 경로를 LLM 실행·completion review에서 검토하며, 실제 누락 입력이 있는 `ask_user`만 `awaiting_user`가 됩니다.
- live smoke는 WebUI approval-required/artifact side effect를 자체 승인하지 않습니다. 읽기 전용 시나리오와 사용자에게 전달된 failure report는 자동 검증할 수 있지만, side effect와 Telegram external delivery는 exact target·권한·각 operation의 명시적 승인 없이는 release acceptance 미완료로 남깁니다. capture-only 승인은 외부 delivery 승인으로 재사용하지 않습니다.
- `failure_tool` live 결과는 일반 성공으로 바꾸지 않습니다. exact run의 `exhausted` 실행 결과, LLM이 판정한 `paths_exhausted`, 정확히 한 번 전달된 사용자 보고를 모두 확인할 때만 기대된 실패 시나리오를 통과시킵니다. 등록되지 않은 Tool 호출을 모델에 노출해 audit 실패를 만들지 않으며, 별도 adapter receipt가 없을 때는 이 정규 canonical exhaustion 조합에서 bounded `unsupported_capability` smoke receipt를 투영합니다. 실행 실패와 사용자 보고 전달은 별도 semantic 상태로 유지합니다.
- 같은 build의 controlled WebUI 읽기 전용 acceptance는 `basic_query`, `web_skill`, `failure_tool`을 각각 독립 실행해 first/terminal latency와 semantic execution/delivery 상태를 결속합니다. `web_skill`은 policy가 승인한 `web_search`와 같은 Skill의 `web_fetch`만 모델에 노출해야 하며, `failure_tool`은 required Tool evidence가 없는 설명문을 성공으로 인정하지 않습니다.
- capability admission evidence는 solution-plan 전용 admission receipt를 우선 사용하고, LLM intake가 명시한 method로 만든 실행 범위에서는 그 범위가 실제로 참조하는 canonical intake plan-policy receipt를 사용합니다. recovery policy receipt나 로그 이벤트는 capability 승인 증거로 인정하지 않습니다.
- request-flow smoke는 canonical self-solve 실행과 실제 delegated topology 실행을 모두 유효한 실행 경로로 인정합니다. `topologyRunCreated`는 관측 정보이며, 위임이 선택되지 않은 실행에 topology run 생성을 강제하는 완료 조건으로 사용하지 않습니다.
- 같은 idempotency key로 진행 중인 channel smoke를 다시 요청하면 새 실행을 시작하지 않고 동일 active run reference를 반환합니다. 같은 key에 다른 request fingerprint를 결속하려는 요청은 거절하며, key hash와 fingerprint는 public metadata에 노출하지 않습니다.
- 채널 런타임 등록은 실제 polling 시작 완료를 기다리지 않고 먼저 활성 채널로 올려, scheduler 같은 내부 기능이 같은 프로세스 안에서 곧바로 채널을 사용할 수 있게 합니다.
- Telegram 쪽 chunk 텍스트/파일/tool status 전달은 `channels/telegram/chunk-delivery.ts`로 분리해, 채널 엔트리와 실제 전달 경계를 나누기 시작했습니다. WebUI approval projection은 server `expiresAt`, user-facing operation scope와 exact-target binding 여부를 표시하되 raw target과 params는 숨깁니다.
- 카메라 artifact는 공개 Tool 결과에 로컬 경로를 넣지 않습니다. WebUI/Telegram delivery adapter가 같은 run에 결속된 opaque artifact ref를 artifact metadata에서 해석한 뒤에만 내부 경로를 사용하며, 다른 run/request-group의 ref와 저장소 밖 경로는 거부합니다. capture evidence와 실제 channel delivery receipt는 같은 run의 서로 다른 단계로 유지합니다.
- WebUI/Telegram chunk delivery는 artifact를 먼저 보낸 뒤에도 `llm_reviewed` canonical final answer를 정확히 한 번 허용합니다. 도구 원문과 검토되지 않은 모델 텍스트는 계속 차단하며, artifact 또는 진단용 fallback 전달은 final answer 소유권을 가져가지 않습니다.
- `camera-acceptance.ts`는 기본 channel smoke manifest와 분리된 opt-in 검증 경계입니다. 자연어 의미를 판정하지 않고, WebUI/Telegram의 run/request-group, capability admission, exact target, capture/delivery approval, one capture, artifact post-check, delivery receipt, completion review와 final answer observation이 같은 구조화 계약을 따르는지만 검사합니다.
- `start-root-run-conversation-probe.ts`는 acceptance 시작을 실제 `startRootRun` composition root에 연결하고 exact run/request-group/session binding만 반환합니다. `camera-conversation-probe.ts`는 active/consumed approval, capability admission, canonical outcome, side-effect receipt count와 opaque artifact metadata의 bounded repository facts를 frozen pre/post-effect snapshot으로 투영해 공통 conversation verifier와 camera validator에 함께 공급합니다. Telegram 전달 승인은 캡처 전과 검증된 artifact가 생긴 직후 모두 별도 operation이 시작되기 전까지 `not_started`입니다. 전달 operation이 시작되면 capture 승인과 다른 approval ref, 현재 채팅에서 파생한 opaque destination fingerprint, 같은 verified artifact ref가 모두 일치할 때만 `awaiting` snapshot을 만들며 capture 승인을 합성하거나 재사용하지 않습니다. 완료 snapshot은 exactly-one provider delivery receipt 뒤의 distinct completion-review receipt, reviewed final-response receipt와 exactly-one root final delivery가 모두 있을 때만 `succeeded/delivered`를 투영합니다.
- Telegram delivery 실패 composition은 같은 승인/dispatcher/artifact repository를 사용합니다. delivery 승인 거부·만료·abort는 provider send 전에 끝나고, transport failure는 한 번의 provider 시도 뒤 delivery receipt 없이 종료됩니다. 이 단계의 실패는 camera permission/capture 실패로 재분류하지 않으며 보존된 verified artifact와 별도 delivery stage evidence를 후속 LLM completion review에 넘깁니다.
- 같은 방향으로 CLI도 별도 chunk 출력 helper를 쓰기 시작했고, 채널별 전달 책임을 entry 파일 밖으로 빼는 패턴을 맞춰가고 있습니다.
- Telegram/Slack/Discord runtime은 활성 채널 여부만 보지 않고 최근 시작 시각, 중지 시각, 마지막 오류, 오류 시각을 함께 보존합니다. 설정 API는 이 snapshot을 그대로 내려 UI가 runtime 상태를 빠르게 표시할 수 있게 합니다.
- Slack/Telegram/Discord stop 경로도 런타임 캐시의 `lastStoppedAt`을 갱신합니다. `runs/preflight.ts`는 이 런타임 스냅샷을 이용해 채널이 죽은 상태에서 새 요청이 execution queue로 들어가지 않도록 빠르게 막습니다.

## 메모

- 채널 코드는 외부 메시지를 core의 session과 run으로 번역하는 역할에 집중해야 합니다.
- 작업 실행 규칙 자체는 `runs`와 `agent`에 남겨두는 것이 맞습니다.
- adapter에서 지원하지 않는 기능은 예외 흐름이 아니라 `unsupported_capability` delivery receipt 또는 capability fallback으로 표현합니다. UI/ledger/detail에는 어떤 capability가 미지원인지와 사용자가 선택할 수 있는 fallback을 짧게 보여줘야 합니다.
